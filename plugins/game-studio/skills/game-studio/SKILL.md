# Game Studio

Preserve the user's chosen engine, platform, and existing project conventions. For a new game with no chosen stack, select a suitable runtime from the intended experience, target devices, available tools, and delivery needs. General Game is an engine-independent workspace; it does not require Web output.

## Match The Task

- `create`: deliver a complete playable core loop with clear controls, progression, success or failure, restart, intentional art, and player feedback.
- `feature`: identify existing state owners and integration points, implement the requested behavior, and check nearby regressions.
- `bugfix`: establish evidence, identify the cause, make a focused fix, and replay the affected flow.
- `polish`: connect art, audio, input, or performance work to a specific player-facing improvement.
- `refactor`: improve boundaries while preserving observable gameplay.

Discussion, design-only, graybox, no-generation, and explicitly requested procedural art override the corresponding creation defaults. Applications, tools, and content requests use an appropriate workflow rather than the full game creation process. A focused change does not require a redesign or new art unrelated to that change.

## Create A Game

1. Read the workspace. When game design or asset planning needs a canvas, use `canvas_initialize` if none exists, then follow its instructions. Discuss with the user until the player fantasy and core loop converge — use the `questionnaire` tool when a concrete design choice needs a decision — then establish primary actions, controls, progression, success/failure/restart behavior, first playable scope, and visual direction. Answer two questions with the user during the discussion and record them as dedicated sections in the main design document: **Why players choose this game** — how this game differs from similar games with mature gameplay (theme, art, mechanical variation, feel, audience); when no credible difference exists, say so and propose a change of direction instead of building a clone — and **Skills and capabilities required** — the skills and capabilities this game needs (art generation, sprite animation, audio, physics, balance, saves, ports), each marked available, tool-producible, externally needed, or missing. **During design analysis, automatically identify VFX requirements based on game mechanics: if the design includes attacks, magic, combat, explosions, status effects, UI feedback, or environmental effects, add a "VFX Requirements" section to the design document listing each effect with its gameplay role, timing, and visual style. For each VFX requirement, automatically map to pixelfx categories (fire/ice/lightning/explosions/impacts/arcane/holy/shadow/status/ui/weather) and note this in the asset list.** Media generation stays blocked until both sections are recorded. Record the design and an asset list with gameplay roles, specifications, sources, and runtime destinations in the canvas main design document. Keep balance numbers and configuration lists in canvas tables (`canvas/tables/<tableId>.json`) instead of code constants: load each table once at startup through the column IDs, and note that a table save reloads the preview page automatically so saved tuning takes effect without code changes. Build on an existing design when present. Then tell the user the design is on the Design tab at the top of the workspace — say this explicitly so they know where to look. Once both required sections are recorded the design is treated as approved automatically and generation can start right away; see Design Gate.
2. Establish a cohesive palette, typography, composition, and feedback language. Use key-screen mockups when substantial visual decisions need them. Save canvas generation nodes with dimensions, purposes, and shared references; generate through `generate_canvas_media` and inspect the outputs. Mockups guide implementation and do not fulfill the production asset list.
3. Reuse suitable assets and generate missing production art for the game's main subjects and themed UI. For frame-based 2D character or effect animation whose poses genuinely change (walk, run, attack, jump, cast), generate one sprite sheet with a fixed multi-cell grid instead of separate per-frame images, and keep the frame count, grid, cell size, background, scale, and anchor consistent with the runtime animation metadata. Drive micro-animations (idle breathing, hover, float, pulse, blink) from one frame in code or procedural transforms instead of generated sheets (see `../web-game-studio/skills/sprite-pipeline/SKILL.md`), and give every generated sheet an explicit per-frame pose-difference list so frames do not repeat. Review production art with the user one asset at a time: present each output as it is generated, integrate it only once it passes review, and when the user rejects an output capture their stated reasons and regenerate accordingly instead of batching a whole set first. Keep sprite identity, frame sizes, anchors, and timing consistent; normalize 3D scale, axes, pivots, materials, and animation names for the chosen engine. Use code drawing for simple geometry, particles, and dynamic UI, or for explicitly requested procedural art. **For VFX implementation, automatically use pixelfx (see `../web-game-studio/skills/pixelfx/SKILL.md`) based on the VFX requirements identified in the design document. When implementing game mechanics, automatically integrate effects: attacks → impacts/melee categories, magic → arcane/fire/ice/lightning categories, explosions → explosions category, status effects → status category, UI feedback → ui category. The pixelfx library provides 244+ ready-to-use effects with dual-buffer rendering and seeded randomness - use it as the default VFX solution unless the user explicitly requests otherwise.** Prepare and import assets through the engine's real pipeline, then integrate them into the playable loop. Keep significant implementation decisions reflected in the design document.
4. Exercise the primary actions, progression, failure/restart, and affected device sizes using available runtime tools. Compare actual gameplay screenshots with the visual direction. Check the asset list against real files and runtime usage; mockups, empty generation nodes, and unused files do not establish completion. **During visual QA, automatically check VFX coverage: verify that all game mechanics have appropriate visual feedback (attacks have hit effects, magic has spell effects, explosions have particle effects, UI interactions have feedback effects). If VFX coverage is insufficient or game feel is weak, automatically recommend specific pixelfx effects to enhance the experience.** Fix shortcomings and repeat the affected checks.

When a required generation tool is unavailable or fails, use a coherent substitute and disclose the remaining gap. Implementation convenience alone is not a reason to replace required production art with placeholders. Do not retry an unchanged failing generation indefinitely.

## Design Gate

- Agent media generation tools (`generate_canvas_media`, `generate_image`, `generate_video`, `generate_3d_asset`, `animate_3d_asset`, `generate_speech`, `generate_sound_effect`, `generate_music`) are hard-blocked until the main design document is complete. A complete document — one recording both required sections — is treated as human-approved automatically; there is no confirmation step to wait for. With no main design document the gate stays closed — create one, complete it, and do not work around the gate.
- A complete design covers the visual direction too: embed at least 2 visual mockups (generated reference images or code-rendered stills) in the main design document before heavy art production, so look and layout are settled early — prose-only directions reliably return as art/layout rework after implementation.
- The gate re-reads the document on every media call: recording the required sections opens it, removing them closes it again, and ordinary edits never reopen anything. No user action is ever needed.
- Manual generation from the canvas UI is not blocked; the gate governs agent-driven production only. `asset-canvas` projects are exempt.

## Specialist Work

- For engine choice, state ownership, input, saving, or performance boundaries, read [Game Foundations](../game-foundations/SKILL.md).
- For playtest scope, runtime evidence, regression paths, or visual QA, read [Game QA](../game-qa/SKILL.md).
- Use relevant installed engine Skills or Connections when available. Follow the workspace's own authoring contract, including Playable Nodes rules for Interactive Story. These optional enhancements do not replace the engine-independent workflow.

For a single-domain request, use the relevant specialist directly. Keep one plan and one definition of done for mixed work. Verification must match available tools; never claim gameplay or visual checks that were not performed.
