# game-metrics-unit-economics — 小体量产品的指标与单位经济

原框架（whale/dolphin 分层、Redis + BigQuery 管道、5 分钟实时 dashboard、ML 留存预测）
是给有百万 DAU 的运营团队用的，对单人开发者的几百到几千 DAU **完全无效**。本 skill 只讲
在这个量级下真正能做的决策。

## 铁律

1. **只用拿得到的数据。** 用户能看的只有：App Store Connect、Google Play Console、
   Firebase/自建埋点、RevenueCat（订阅）、AdMob（广告）、Steam/SteamDB。
   任何建议若需要先搭数据仓库、自建后端聚合、上 ML 模型 → 一律否决，那是浪费开发时间。
2. **小样本不做显著性检验。** 几百个用户跑不出 p < 0.05。不要建议 A/B 测试作为主要决策手段，
   更不要编造 p-value。改用下面「小流量下的对比方法」。
3. **禁止编造数字与基准。** 报告里的每个数值要么来自用户提供的后台截图/导出，要么带来源 URL +
   检索日期。行业基准必须标注"网络常引用的粗略区间，非权威，且品类差异极大"。
4. **指标为决策服务。** 每个指标都要回答"看到它会做什么动作"。答不出来的指标不要埋、不要看。
5. **先看钱，再看留存。** 单人开发者的第一问题是「这产品能不能产生正的单位经济」，
   不是「玩家喜不喜欢」。

## Step 1 — 确认数据可得性（先问，别假设）

用环境可用的澄清工具（如 `question`）或直接问：

- 产品**上线了吗**？（未上线 → 跳到 Step 2 做埋点设计；已上线 → 先要数据）
- 有哪些后台权限：ASC / Play Console / Firebase / RevenueCat / AdMob？
- 能否提供导出 CSV 或截图？（有真实数据时，一切分析基于它，不要用估算替代）
- 变现模式：付费下载 / 订阅 / 消耗型 IAP / 广告 / 混合？价格？
- 累计安装、当前 DAU/MAU 量级？（决定下面哪些方法可用）

若用户给不出任何真实数据，明确告知："在没有后台数据的情况下我只能给判断框架和基准区间，
不能给结论"，然后按框架输出，**不要**用假设数字算出一个看起来精确的收入预测。

## Step 2 — 上线前：最小埋点清单

**上限 12 个事件**。超过就是在给自己加负担、给隐私合规加风险、给分析加噪音。

必备（所有产品）：

| 事件 | 关键参数 | 用来回答 |
|---|---|---|
| `app_open` | 首次/回访、来源 | DAU、留存、归因 |
| `onboarding_step` | step_id, 完成/放弃 | 首启流失在哪一步 |
| `onboarding_complete` | 耗时 | 激活率（北极星分母） |
| `core_action` | 该产品的核心动作（如 `level_complete` / `report_generated`） | 核心价值是否被触达 |
| `core_action_fail` | 失败原因/关卡 id | 难度尖峰、卡点 |
| `paywall_view` | 触发场景 | 付费漏斗第一环 |
| `purchase_start` | 商品 id、价格档 | 意向 |
| `purchase_success` | 商品 id、实收、是否首购 | 转化率、ARPPU |
| `purchase_fail` | 错误码 | 支付链路问题（常被忽略，掉钱） |
| `session_end` | 时长 | 会话长度 |

按需（最多再加 2 个）：`ad_impression` / `ad_revenue`（广告变现）、`feature_used`（判断某个
功能是否值得继续维护——**没人用的功能应当删掉以省维护成本**）、`share_or_invite`（自传播）。

**明确不要埋**：热图、点击坐标、UI 元素级交互、页面停留时长矩阵、玩家分层画像、
任何需要 ML 才能用上的高维特征。单人开发者分析不过来，纯负担。

实现建议（按技术栈）：Flutter → `firebase_analytics`（FlutterFire）；
Phaser/Web → Firebase JS SDK 或 Plausible/Umami（隐私友好、无需 Cookie 弹窗，适合 Web）；
订阅事件统一从 RevenueCat webhook 取，比客户端埋点可靠。

## Step 3 — 隐私合规（上线前必须过一遍）

- **iOS ATT**：若用广告或跨 App 追踪，必须弹 `AppTrackingTransparency`；不弹 = AdMob 收入归零
  或账号风险。若完全不做追踪 → 不弹窗，eCPM 会低，但省合规成本，需权衡。
- **GDPR / CCPA**：隐私政策 URL（ASC 与 Play 都强制要求）、数据删除入口、
  Firebase 需关闭/匿名化 `user_id` 中的个人信息。
- **Play Data Safety / App Privacy「营养标签」**：如实申报，申报错误是拒审与下架的常见原因。
- **COPPA**：若产品可能被儿童使用（尤其休闲/益智游戏），要么明确不面向儿童并设置年龄门，
  要么关掉个性化广告 —— 二者必选其一，不能含糊。
- 不要采集精确位置、通讯录、设备指纹；采集了就要申报，申报了就会增加审核与合规成本。

## Step 4 — 选北极星指标（按变现模式）

| 变现模式 | 北极星 | 关键辅助指标 | 主要死因 |
|---|---|---|---|
| **订阅** | 付费订阅数（净增） | 试用开始率、试用→付费转化率、月流失率(churn)、MRR | 试用转化低 + churn 高 → LTV 撑不起 CPI |
| **付费下载** | 净销售额 | 商店页转化率(展示→安装→付费)、退款率、地区分布 | 转化率与退款率；无试用意味着商店页文案决定一切 |
| **IAP（非订阅）** | ARPPU × 付费用户数 | 首购时间、复购率、各档位销量分布 | 付费率通常极低（个位数百分比），需足够装机量 |
| **广告** | DAU × 人均展示 × eCPM | 会话数/日、展示频次、eCPM 地区差异 | DAU 不够则收入必然微薄；eCPM 地区差异常达 5–10 倍 |

**订阅是单人开发者最优变现模式的常见选择**（可预测 MRR、Apple/Google 都给它更好的商店曝光），
但前提是产品有**持续使用理由**。一次性工具类强行做订阅会招致差评与高退款。这条要如实告诉用户。

## Step 5 — 单位经济实算

```
毛收入            = 付费用户数 × ARPPU
平台抽成后        = 毛收入 × (1 - 抽成率)      # 抽成率须核实当前官方政策：标准档 30%，
                                              # Apple Small Business Program / Google Play
                                              # 的 15% 档有年收入门槛与注册要求
实收              = 平台抽成后 - 退款 - 税费影响 - 支付/汇率损耗
LTV               = 实收 / 新增用户数（按同期 cohort 计）
付费下载 LTV      ≈ 价格 × (1 - 抽成) × (1 - 退款率)
订阅 LTV          ≈ 月费 × (1 - 抽成) × (1 / 月churn)   # 平均生命周期 = 1/churn
广告 LTV          ≈ 日均展示 × eCPM/1000 × 平均活跃天数
CAC               = 获客支出 / 新增付费可得用户；自然量 CAC ≈ 0，但要计入你自己的工时机会成本
判定              : LTV/CAC ≥ 3 才谈得上健康的买量；< 1 → 买量路径关闭，只能走自然量
```

抽成率、退款率、eCPM、税率**一律现场核实**（用可用的 web 搜索工具查官方页面，或用用户
后台数据），不要凭记忆填。核实后在输出里标注日期。

## Step 6 — 留存与转化的判读

网络常引用的粗略基准（**非权威，品类差异极大，用前请核实；此处只用于量级判断**）：
休闲手游 D1 留存常在 30–45%、D7 在 10–20%、D30 在 4–8% 区间；中重度更低；
工具类看的是「任务完成率」而非 D30 留存。订阅试用→付费转化常在几十个百分比的量级内浮动，
低于该量级说明价值主张没在试用期内被感受到。

判读原则（比背数字有用）：

- **D1 低** → 首启体验/上手成本问题，改 onboarding，不是改内容量
- **D1 尚可但 D7 崩塌** → 核心循环缺乏重复理由，这是**结构性问题**，加内容治不好，
  通常需要 Pivot 或砍项目
- **留存好但不付费** → 变现点错位（付费墙位置/价格/价值感知），这是**最好修的一类问题**
- **展示量高但安装转化低** → 商店页（图标/截图/前三行文案/视频）问题，用 Play 商店实验或
  ASC 的 Product Page Optimization 修，成本极低收益高
- **安装高但激活低** → onboarding 流失，看 `onboarding_step` 漏斗

## Step 7 — 上线后复盘节奏与 kill 判定

| 时点 | 只看这几件事 | 决策 |
|---|---|---|
| **D1–D7** | 崩溃率、支付链路是否通（`purchase_fail`）、onboarding 漏斗、有无自然安装 | 修致命 bug；不要动设计 |
| **D30** | 激活率、D1/D7 留存、付费转化率、商店页转化率、自然安装趋势 | 判断是"产品问题"还是"分发问题" |
| **D60–D90** | LTV/CAC、MRR 或月净收入、留存曲线是否走平、评论星级与主题 | **执行 kill criteria** |

kill 判定必须对照 `game-market-validation` Step 5 里预先写下的条件。若当时没写，
现在补一个客观条件（例：「D90 时月净收入 < 你当地一个月生活成本的 1/3，且月自然安装无增长
→ 停止投入」），并**严格执行**。这个 skill 的重要职责之一是在用户想继续加注沉没成本时，
用他自己之前定的标准拦住他。

**继续投入的正当理由只有三种**：单位经济已为正（可放大）、留存好但变现未修（可修）、
有明确且低成本的分发突破点（可做）。其余「再改改看看」都是沉没成本谬误。

## Step 8 — 小流量下的对比方法（替代 A/B 测试）

流量不足以做统计检验时，用这些：

1. **平台自带商店实验**（首选）：Google Play 的 Store Listing Experiments、
   App Store 的 Product Page Optimization。平台负责分流与统计，你只提供素材变体，
   且直接影响转化率——这是单人开发者性价比最高的实验。
2. **前后对比 + 足够长的窗口**：改动前后各取 ≥2 周同口径数据，排除节假日/推荐位/版本发布
   等干扰。承认这不是因果证明，但比不做决策好。
3. **只做大效应量改动**：一次只改一件大事（价格、付费墙位置、图标），
   不做 2% 级别的微调——微调在这个样本量下永远读不出信号。
4. **定性优先**：10 条真实用户评论/邮件/Reddit 反馈，在几百 DAU 量级下比任何指标都更有信息量。
   主动去评论区、subreddit、Discord 读原话并摘录。
5. **分段而非分组**：按地区、机型、来源渠道分段看差异（这些分段天然存在，不需要分流），
   常能发现"某个国家/某个渠道的用户明显更愿付费"，直接指导定价与投放。

明确告诉用户：**不要**为了做 A/B 测试去搭分流系统、写实验框架、上 Bayesian 计算。

## 反模式（见到就拦）

- 搭 ClickHouse/BigQuery/Postgres 聚合管道、写 ETL、做实时 dashboard
- 做 whale/dolphin/minnow 分层（这个体量根本没有 whale）
- 训练 churn 预测 / LTV 预测模型
- 埋 50 个事件、上热图工具、做用户画像聚类
- 用估算数字算出精确到千位的收入预测
- 在 D7 留存结构性崩塌时讨论"再加 20 个关卡"
- 为了指标好看而做促销/降价，却没算清对 LTV 与退款的影响

## 输出

- 有真实数据时：输出**判读 + 下一步 3 个动作**（按性价比排序），动作要具体到"改哪个文件/
  哪张截图/哪个价格档"。不要把数据复述一遍。
- 无真实数据时：输出埋点清单 + 该变现模式的指标表 + 合规清单 + 复盘节奏表，并明确标注
  "以下为框架，非结论"。
- 报告落盘到项目内 `docs/metrics/<slug>-review-YYYYMMDD.md`；对话里先给结论和动作。
- 语言：简体中文；指标名、事件名、平台专有名词保留英文。
