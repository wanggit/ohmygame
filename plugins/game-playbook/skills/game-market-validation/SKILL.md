# game-market-validation — 立项前的盈利可行性评估

产出物是**决策**，不是文档堆。默认前提：用户是中国大陆单人/小团队独立开发者，面向海外市场
（App Store 海外区 + Google Play + Web），无国内发行资源、无买量预算或预算极小。

## 铁律（违反即让本次评估失效）

1. **禁止编造任何数字。** 每一个数值（市场规模、下载量、评分、评论数、价格、CPI、留存、eCPM）
   必须带 `来源 URL + 检索日期`。查不到就写 `未验证`，并说明"该数据只能从 X 获取，路径是 Y"。
   绝不因为模板里有个空格就去填一个看起来合理的数。
2. **默认悲观。** 独立开发者的基线结局是「下载量三位数、收入不足覆盖服务器成本」。任何乐观结论
   都要有具体证据支撑，而不是"这个品类很火"。
3. **不迎合。** 用户对自己的 idea 有感情，但结论必须客观。若判定 No-Go，直接说 No-Go 并给理由，
   同时给 1–2 个更可能赚钱的替代方向；不得为了照顾情绪而弱化成"有挑战但可行"。
4. **区分「市场大」和「你能拿到」。** TAM 大与单人开发者能赚到的钱无关。始终落到
   SOM：以你的获客能力，第一年现实能拿到多少付费用户。
5. **额度纪律。** 用环境里可用的 web 搜索工具（如 Tavily 的 `tavily_search`；其他等价搜索
   工具同理）时，一轮评估控制在 2–3 次深度检索以内，先用浅检索探路。读单个已知 URL 用可用的
   网页抓取工具直接读，不消耗搜索额度。

## 工作流

### Step 0 — 澄清（最多一轮，用环境可用的提问/澄清工具，若无则直接在对话中提问）

必须先问清，否则后面全是空转。一次问完这几项（用户已说明的不要重复问）：

- **品类与玩法一句话**：具体到子品类（不是"休闲游戏"，而是"数字合成类放置 + 离线收益"）
- **平台**：iOS / Android / Web / Steam / 多端
- **变现设想**：付费下载 / 订阅 / IAP / 广告 / 混合；有没有想好价格
- **可投入的开发周期**：几周还是几个月（决定成本回收门槛）
- **获客预算**：0 / < $500 / 更多；有没有已有的受众渠道（X、YouTube、TikTok、Reddit、邮件列表）
- **同类已上架作品**：用户自己知道的对标产品

若用户只丢来一句话就要求评估，先做 Step 1–2 的粗筛，粗筛结果明显为 No-Go 时直接告知，
不必追问全部细节（省双方时间）。

### Step 1 — 付费意愿验证（最关键，先做这步）

回答三个问题，每个都要证据：

1. **谁会为这个付钱？** 具体人群画像 + 该人群在同类产品上**已经付过钱**的证据
   （竞品有付费档且活着、评论区提到"值得这个价"、订阅数/畅销榜排名可查）。
   若同品类**没有任何**成功付费产品 → 强烈危险信号，要么品类不适合付费，要么需求是伪需求。
2. **付多少？** 竞品实际定价与内购档位（从商店页面直接读，不要猜）。给出该品类的价格带。
3. **凭什么付给你而不是现有产品？** 差异化必须是**用户能感知且愿意为之付钱**的差异，
   不是"我用 Flutter 写的所以更快""我美术更好看"。若答不出来 → No-Go 或 Pivot。

**免费用户 ≠ 潜在收入。** 明确区分「有人想要」和「有人付钱」。工具类 App 尤其容易踩这个坑：
高下载低转化的品类，广告 eCPM 又低，等于白做。

### Step 2 — 竞品真实表现盘点

找 **5–8 个**竞品：3–5 个直接竞品（同品类同平台）+ 2–3 个替代品（用户满足同一需求的其他方式，
包括"不玩/不用"）。用公开可验证的**代理指标**，不要引用需付费数据库才有的营收估算当事实：

| 代理指标 | 从哪拿 | 说明 |
|---|---|---|
| Google Play 下载量区间 | 商店页面公开显示 `100,000+` | 免费、可靠的下限 |
| 评分 + 评论总数 | App Store / Play / Steam 页面 | 评论数是装机量的粗代理 |
| **评论增速** | 页面「最近更新」+ 历史快照（Wayback Machine） | 判断是活的还是死的，比总数更有用 |
| 最近更新日 / 版本节奏 | 商店页面 Version History | 超过 6–12 个月未更新 = 团队放弃或已盈利躺平，需辨别 |
| 榜单名次 | App Store 分类榜 / Play 分类榜 / 免费榜畅销榜 | 能进分类榜前 100 才有像样自然量 |
| Steam 同时在线 / 评论数 | SteamDB、Steam 页面 | Steam 品类的标准代理 |
| 社区规模 | Discord 成员数、Reddit 订阅数、X 关注数 | 判断是否有真实粉丝盘 |
| 差评主题 | 商店 1–3 星评论 | **金矿**：竞品的差评就是你的机会点，逐条摘录原文 |
| 内购档位与订阅价 | 商店页面 IAP 列表 | 直接抄价格带，不要猜 |

产出竞品表（每行一个竞品，每列一个指标 + 来源）。**竞品差评摘录至少 5 条原文**，
这是差异化机会的唯一可靠来源。

### Step 3 — 单位经济测算（明示假设链）

不要给一个孤立的"预计第一年收入 $X"。给**可追溯的假设链**，让人能反驳其中任一环：

```
展示量 → 安装转化率 → 激活率 → 付费转化率 → ARPPU → 毛收入 → 扣平台抽成/退款/税 → 净收入
```

每一环写清：取值、来源（`未验证` 就标明）、以及"若这一环实际值减半，结论如何变"。

必算的两条对照线：

- **LTV**（单用户生命周期净贡献，已扣平台抽成与退款）
- **CAC / CPI**（获客成本）：分「付费买量 CPI」与「自然量 CPI（≈0 但需内容/ASO 投入工时）」两种

判据：**LTV / CAC < 1 → 买量路径直接不可行**，只能走自然量；此时评估重心必须转到
"你有没有能力持续产出内容/做 ASO"，而不是产品本身。

平台抽成按当前官方政策核实（Apple Small Business Program / Google Play 的 15% 档有年收入门槛，
标准 30%；退款率、增值税/销售税由平台代收但影响实收）。**这些数字会变，写报告时用可用的
web 搜索工具核实官方页面并注明日期，不要凭记忆填。**

给三档（保守 P90 / 现实 P50 / 乐观 P10），但**保守档必须真的保守**——保守档 = 无推荐位、
无买量、仅靠 ASO 与少量社区发帖的自然结局。多数独立产品的真实落点在保守档以下。

### Step 4 — 获客路径可行性（独立开发者的真正瓶颈）

产品做得出来不等于有人知道。逐条评估这些渠道对该品类的现实可行性，并给**具体动作**而非口号：

- **ASO**：关键词竞争度（用商店搜索结果第一页的产品评论数量级判断）、标题/副标题可占的词
- **Reddit / 论坛**：该品类有哪些 subreddit、规模、是否允许开发者自推（很多禁止）
- **TikTok / YouTube Shorts / X**：玩法是否「一眼看得懂 + 有视觉钩子」。若核心乐趣需要 5 分钟
  才能体会到 → 短视频渠道基本无效，这是致命伤
- **Product Hunt / Hacker News**：仅对工具类、开发者向、Web 产品有效；对休闲游戏几乎无效
- **付费买量**：AdMob / AppLovin / Meta，按 Step 3 的 LTV/CAC 判断是否可能为正
- **平台推荐位（Apple Featuring / Play 推荐）**：不可依赖，但可作为上行期权；说明申请路径
- **交叉推广 / 发行商**：若走发行，抽成通常 30–50%，重算单位经济

**若所有渠道都依赖"运气"或"爆款视频"，结论应为 No-Go 或 Pivot**，因为这不是可复制的路径。

### Step 5 — 结论与落盘

给出：

1. **GO / NO-GO / PIVOT**（三选一，不许"看情况"）
2. **一段话理由**：最关键的 1–2 条决定性证据
3. **可证伪的 kill criteria**：例如"上线 60 天内 D7 留存 < 12% 且自然安装 < 300/月 → 停止投入，
   不做 v2"。必须写成能被客观判定的条件 + 时间点。这是本 skill 最有价值的输出，
   防止用户在沉没成本上继续加注。
4. **若 NO-GO**：给 1–2 个替代方向，每个附一句话说明为什么更可能赚钱（同一批证据反推）。
5. **若 GO**：给「最小可验证版本」范围——能验证核心付费假设的最小功能集，以及验证需要多少周。
   明确反对为了完整度而延长开发周期。

报告写入项目内 `docs/market/<slug>-market-validation.md`（无项目目录时写到当前工作目录并在
回复中说明路径）。报告用简体中文，竞品名/商店文案/关键词保留英文原文。

**回复用户时先给结论（GO/NO-GO + 一句话理由 + kill criteria），再问是否要看完整报告**，
不要把整份报告贴在对话里。

```markdown
# <产品名> 盈利可行性评估
检索日期：YYYY-MM-DD ｜ 结论：GO / NO-GO / PIVOT ｜ 置信度：高/中/低

## 一、结论与理由
（3–5 行，含决定性证据）

## 二、Kill Criteria（可证伪）
- 条件 1（指标 + 阈值 + 时间点）→ 动作
- 条件 2 → 动作

## 三、付费意愿
谁付钱 / 付多少（竞品价格带表）/ 凭什么付给你

## 四、竞品盘点
| 竞品 | 平台 | 下载量区间 | 评分(评论数) | 定价/内购档 | 最近更新 | 社区规模 | 来源 |
（+ 竞品差评摘录 ≥5 条原文，标注可切入的机会点）

## 五、单位经济
假设链表 → LTV → CAC/CPI → LTV/CAC 判定
| 档位 | 第一年安装 | 付费转化 | 净收入 | 关键假设 |

## 六、获客路径
| 渠道 | 可行性 | 具体动作 | 预期量级 | 依据 |

## 七、风险与反证
（列出最能推翻本结论的 3 条证据缺口，以及如何低成本补上）

## 附录：数据来源
（URL + 检索日期 + 该来源支撑了哪个数字）
```

## 红队自查（写完报告前逐条过）

- 我有没有把"品类市场规模"当成"我能拿到的收入"？
- 有没有任何一个数字是我推测出来的却写得像事实？→ 改成 `未验证`
- 保守档是不是其实挺乐观？（保守档不该出现推荐位、爆款视频、KOL 自发传播）
- 差异化是不是只有开发者自己感知得到（技术栈、代码质量、"更用心"）？
- 是否忽略了替代品？（用户当前的解决方式，包括"忍着不用"和"用免费的 X"）
- 若这个 idea 已被大厂/头部独立开发者做过且失败了，我有没有查？（搜 `<品类> shutdown`、
  `<竞品> discontinued`、Reddit 上的 post-mortem）
- 我是不是在帮用户论证他想要的结论，而不是在检验它？

## 上线之后

产品上架后的指标体系、留存基准、埋点清单、小样本下的 A/B 做法，交给
`game-metrics-unit-economics` skill。本 skill 只负责立项前决策；Step 5 的 kill criteria
应在上线后由那个 skill 的指标来判定。
